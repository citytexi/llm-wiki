# 위키 운영 진입점

**위키 작업(ingest/query/lint/research/delete-source/add-domain 중 하나, 또는
`wiki/`·`raw/` 아래 파일 편집) 을 시작하기 전에는 반드시 `wiki/script/route.py`를
돌린다.** "자체 지식으로 처리할 수 있을 것 같다"는 판단으로 이 단계를 건너뛰지
않는다 — 그 판단 자체가 확률적이고, 이 문서의 목적은 그것을 확정적 의무로
바꾸는 데 있다. 데이터 계약은 여기서 되풀이하지 않는다. 정본은
`wiki/conventions.md`다.

## 라우팅 절차 — 7단계

1. 요청과 대화 맥락에서 **도메인**을 판정한다. 판정에 "지금 어떤 파일을
   바꾸고 있는가"는 쓰지 않는다 — 라우팅은 작업을 시작하기 *전에* 하므로
   변경 경로가 아직 존재하지 않는다.
2. 요청을 아래 **의도 8종** 중 하나로 분류한다. 확신이 서지 않으면
   `unclear`로 둔다.
3. `python3 wiki/script/route.py --intent <의도> [--domain <도메인>] [--json]`을
   실행해 `required`·`reference` 후보를 받는다.
4. 지식 그래프 도구(graphify 등)를 설치했다면 관계 보완에 쓴다. 안 썼으면 이
   단계를 건너뛰고 5번으로 간다 — 선택 연동이다. graphify 기준으로 적으면
   `graphify query "<노드명>"`이다.
   요청 표현을 그대로 검색어로 쓰지 않는다 — `graph.json`에 실재하는 노드명만
   골라 쓰고, 비슷한 말을 지어내지 않는다. 매칭되는 노드가 없으면 "관련
   어휘를 찾지 못했다"고 밝히고 그래프 검색을 멈춘 뒤 라우팅 맵 결과만으로
   진행한다. 매칭된 결과 페이지는 seed 후보에 더한다. **노드명은 경로가
   아니다** — `--seed`로 넘기기 전에 저장소 상대 경로로 바꾼다. 변환은
   출력 줄의 `src=` 값(스캔 루트 기준 상대경로) 앞에 `wiki/domains/`를 붙이는
   것이다: `src=inbox/inbox-purpose.md` → `wiki/domains/inbox/inbox-purpose.md`.
   `src=`가 없으면 그 후보를 버린다. 경로가 아닌 값을 넘기면 `route.py`가
   종료 코드 4로 막는다.
5. seed(도메인 `required` 페이지, `--seed`로 넘긴 페이지, 4번 결과)가
   정해지면 `--seed <저장소상대경로>`를 붙여 같은 명령을 다시 돌려 출처
   중복 확장을 받는다.
6. `required`만 읽는다. `reference`는 필요할 때만 연다. 이번 작업에 적용할
   규약이 무엇인지 이 시점에 명시한다.
7. 작업이 끝나면 "작업 후" 절차를 따른다.

## 의도 8종 — 판정 기준

- **ingest** — `raw/`의 새 원본을 위키 페이지로 통합하는 요청.
- **query** — 기존 위키 내용을 조회·답하는 요청. 페이지를 만들거나 고치지
  않는다.
- **research** — 위키에 없는 지식을 웹 검색으로 메우려는 요청. 결과는
  `raw/`에 먼저 저장한 뒤 ingest로 이어진다.
- **delete-source** — 사용자가 `raw/`에서 원본을 이미 지웠고, 연결된 위키
  페이지를 정리해야 하는 요청.
- **add-domain** — 새 도메인을 만드는 요청.
- **lint** — 콘텐츠를 바꾸지 않고 위반 여부만 점검하는 요청.
- **schema-change** — `wiki/conventions.md`가 정의하는 데이터 계약 자체
  (필드, 값 집합, 디렉토리 배치 등)를 바꾸는 요청.
- **unclear** — 위 일곱 중 어디에도 확신이 서지 않는 요청.

## 멈출 조건

`route.py`의 종료 코드가 아래 두 코드(3, 4) 중 하나면 **진행하지 않고
사용자에게 확인한다.** 4 아래 나열된 항목들은 별개의 정지 조건이 아니라 4
하나가 갈리는 원인들이다.

- **3** — 의도가 `unclear`다. 도메인·의도를 짐작으로 채우지 않는다. 단,
  `--seed`를 함께 넘겼는데 그 seed가 해석되지 않으면 3이 아니라 4가 뜬다 —
  seed 오류가 의도 불명보다 먼저, 그리고 우선해서 걸린다(아래 4번째 항목).
- **4** — 라우팅 입력이 잘못됐다. 표준 출력이 아니라 표준 오류의 메시지를 읽고
  원인을 가린다.
  - 의도나 도메인을 모른다 → 새 도메인이면 `add-domain`을 먼저 돌고, 오타면
    정정한다.
  - `--seed`가 수집된 페이지가 아니다 → 저장소 상대 경로로 고친다. graphify
    노드명은 경로가 아니므로 그대로 넘기지 않는다(5단계). 의도가 `unclear`라도
    이 검사는 건너뛰지 않는다.
  - `routing.json`이 실재하지 않는 경로를 가리키거나 `expansion` 블록이
    불완전하다 → 맵을 고친다.
  - `routing.json` 자체가 없거나 JSON 문법이 깨졌다 → 파일 경로와 문법을
    확인한다. 이 경우도 트레이스백이 아니라 이 코드로 끝난다.

(참고: **0**은 정상, **2**는 저장소 루트가 아닌 곳에서 실행했다는 뜻이다 —
저장소 루트로 이동한 뒤 다시 돈다.)

## 읽기 폭

허브 `wiki/index.md`를 통째로 읽지 않는다. 허브에서 도메인 이름만 확인하고
해당 `<도메인>-index.md` 하나만 연다. `route.py` 출력의 `required`가 7개를
넘으면 라우팅이 과하다는 신호다 — 그래도 읽기는 진행하되, 아래 "라우팅 실패
기록" 절차를 따른다.

## 작업 후

`python3 wiki/script/lint.py`를 실행해 위반 0건을 확인한다. 그리고 **어떤
규약을 어느 페이지에 반영했는지**를 구체적으로 밝힌다 — "conventions.md를
읽었다"는 문장은 충분하지 않다. 예: "conventions.md §2의 `partial` 표기
규칙을 `<도메인>-index.md`의 해당 줄에 반영했다."

지식 그래프를 쓴다면 ingest 배치가 끝나고 추출을 1회 돌린다 — semantic 캐시가
파일별로 있어 바뀐 문서만 실제 토큰을 쓴다. graphify 기준으로는
`graphify update <path>`가 코드 전용이라 마크다운 위키 페이지에 안 먹으니
전체 추출을 쓴다. 그래프를 안 쓰면 이 문단은 해당 없다.

## 라우팅 실패 기록

작업 중 라우팅 맵이 놓친 문서를 열었거나, 반대로 필요 없는 문서까지
`required`로 끌려왔다면 `wiki/synthesis/routing-misses.md`에 적고
`wiki/routing.json`을 고친다. 기록하지 않으면 같은 실패가 반복된다.

## 더 읽을 곳

- **데이터 계약(필드, 값, 디렉토리 배치, frontmatter, 민감 데이터 등급)** —
  `wiki/conventions.md`가 정본이다. 이 문서와 어긋나면 `conventions.md`가
  옳다.
- **긴 절차** — `wiki/references/ingest-checklist.md`,
  `wiki/references/cascade-delete.md`, `wiki/references/add-domain.md`,
  `wiki/references/lint-rules.md`, `wiki/references/research.md`. 해당
  의도로 라우팅하면 `route.py`가 알맞은 파일을 `reference`로 알려준다.
- **설계 원리** — `docs/llm-wiki.md`. 스키마 자체를 바꿀 때(`schema-change`)
  가 아니면 열 필요 없다.
